## 1. Microprueba secuencial (ab -n 400 -c 1, php artisan serve, sin concurrencia)
# Una variable a la vez. Tiempo medio por peticion en ms (promedio de 2 a 4 corridas validas).
# "portada" = GET / ; "panel" = GET /patient/dashboard/data autenticado (mas consultas SQL = mas spans).
#
# config                              | portada antes | portada despues | panel antes | panel despues
# A  memoria, OTEL off, single        |   4.39        |   4.32          |   6.50      |   6.53
# R  solo metricas Redis              |   5.60 (+1.2) |   5.35 (+1.0)   |   8.01 (+1.5)|  8.07 (+1.5)
# O  solo OTEL                        |   8.45 (+4.1) |   6.23 (+1.9)   |  11.56 (+5.1)|  8.71 (+2.2)
# J  solo log JSON                    |   4.33 (+0.0) |   4.50 (+0.2)   |   6.49 (+0.0)|  6.61 (+0.1)
# B  todo (redis, OTEL, single,json)  |   9.29 (+112%)|   7.07 (+64%)   |  12.83 (+97%)|  9.71 (+49%)
#
# Desglose de OTEL por peticion (antes): forceFlush() en terminate() = 3.2 ms p50 (3.9 p95), de los
# que ~0.6 ms son el POST HTTP a Tempo y el resto es serializar con google/protobuf en PHP puro
# (~0.6 ms fijos + ~0.15 ms por span, mas cargar los descriptores protobuf en cada peticion).
# Sin forceFlush el costo de OTEL es ~0 (4.5 ms vs 4.4 ms), pero Tempo NO recibe la traza: el
# TracerProvider se construye con el builder y no registra apagado; en PHP cada peticion arranca
# de cero, asi que el BatchSpanProcessor no acumula entre peticiones. Quitar el flush pierde trazas.
# Despues: forceFlush() = 0.96 ms p50 (2.0 p95) con el exportador OTLP/JSON propio.
# Serializacion OTLP medida aparte (6 spans): JSON 1.5 ms, protobuf binario 1.8 ms (google/protobuf
# en PHP puro, sin ext-protobuf): cambiar a application/x-protobuf no ayuda.
# Redis: conexion persistente -0.2 a -0.5 ms; quedan 2 EVAL de Lua por peticion (contador +
# histograma) y cargar Predis. Con ext-redis (phpredis) el costo bajaba a ~0.45 ms (no aplicado:
# anade dependencia de extension). Log JSON: ~0, solo escribe cuando hay registros.

## Conclusion
# La correccion reduce el costo por peticion medido en la microprueba (OTEL +4.1 -> +1.9 ms en portada,
# +5.1 -> +2.2 ms en panel; instrumentacion completa +112 % -> +64 % en portada, +97 % -> +49 % en panel)
# y en las medianas de k6 (+54 % -> +32 %). En el p95 de k6 el ruido de la maquina (+-8 ms entre
# corridas identicas, carga de 2.5 a 13.8) impide demostrar mejora: antes de corregir los pares del
# mismo dia daban +30 % (A0/B0) y +37 % (A0b/B0); despues, +28 % a +70 %. La meta <= +10 % no se cumple.
#
# Detalle:
# - Dominaba OTEL (~80 % del sobrecosto): export sincrono por peticion en terminate(), y dentro de el
#   la serializacion con google/protobuf en PHP puro. Corregido con un exportador OTLP/JSON propio.
# - Segundo, metricas en Redis (~1.0 a 1.5 ms/peticion); la conexion persistente ahorra 0.2-0.5 ms.
# - Log JSON: sin costo medible.
# - Costo restante (~2.7 ms portada, ~3.2 ms panel): export HTTP a Tempo en cada peticion (~1 ms),
#   creacion de spans, 2 EVAL a Redis, todo en el unico hilo de php artisan serve. En php-fpm el
#   export ocurre despues de fastcgi_finish_request(), fuera de la latencia del cliente.
